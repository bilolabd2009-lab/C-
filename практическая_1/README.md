# Практическая 1. Рефакторинг legacy-кода: управление поливом теплицы

Исходный код лежит в [`legacy/greenhouse_legacy.cpp`](legacy/greenhouse_legacy.cpp) и не меняется.
Рефакторинг идёт в [`src/greenhouse.cpp`](src/greenhouse.cpp). Каждый этап сделан отдельным коммитом,
и после каждого все тесты проходят.

| Этап | Что сделано |
|---|---|
| 1. Фиксация поведения | golden-master тесты, эталон записан по legacy-версии |
| 2. Именование и типизация | константы вместо магических чисел, `enum class Action`, коды возврата |
| 3. Выделение чистых функций | правила проверки и расчёта вынесены в `constexpr`-функции, проверены `static_assert` |
| 4. Устранение дублирования вывода | `promptInt`, один общий блок «сообщение + статус» вместо четырёх копий |

## Как запустить тесты

Нужны `g++` (C++17) и Python 3.

```
python tests/run_tests.py            # проверить src/greenhouse.cpp
python tests/run_tests.py --legacy   # проверить исходник (должен проходить всегда)
python tests/run_tests.py --record   # перезаписать эталон по legacy (только если меняется сам набор сценариев)
```

## Этап 1. Фиксация поведения

Перед любыми правками поведение программы закреплено характеризационными тестами (golden master).
[`tests/run_tests.py`](tests/run_tests.py) собирает программу, подаёт на вход 27 сценариев и сравнивает
весь вывод **побайтово** вместе с **кодом возврата**. Эталон в `tests/cases/` (`*.in`, `*.out`, `*.code`)
снят с legacy-версии, поэтому тест проверяет «как было», а не «как должно быть».

Зафиксированное поведение, включая неочевидные моменты, которые рефакторинг обязан сохранить:

| Ситуация | Поведение |
|---|---|
| Влажность не число или ввод пуст | `Input error`, код 1 |
| Влажность вне `0..100` | `Invalid moisture`, код 2 (границы 0 и 100 допустимы) |
| Действие не число или конец ввода до `0` | `Input error`, код 1, итог **не** печатается |
| `0` | выход из цикла, печать итога, код 0 |
| `1` статус | считается операцией |
| `2` открыть | отказ, если клапан уже открыт или влажность ≥ 60; отказ операцией не считается |
| `3` закрыть | считается **всегда**, даже если клапан уже закрыт |
| `4` импульс | отказ, если клапан открыт или влажность ≥ 85; иначе +20 % (не выше 100) и +5 л |
| неизвестный код | `Unknown action`, операцией не считается |
| 8 операций | цикл завершается сам, следующий ввод не читается |
| приглашения `Moisture: ` и `Action 0/1/2/3/4: ` | печатаются без перевода строки |

## Этап 2. Именование и типизация

- Магические числа `0, 100, 60, 85, 20, 5, 8` стали константами `kMinMoisturePercent`, `kOpenMoistureLimitPercent`,
  `kPulseMoistureGainPercent`, `kPulseWaterLiters`, `kMaxOperations` и т. д. В имени есть единица измерения (`Percent`, `Liters`).
- Коды действий `0..4` стали `enum class Action`. У него фиксированный базовый тип `int`, поэтому приведение
  неизвестного кода (например `9` или `-1`) определено и просто попадает в ветку `Unknown action`.
- Коды возврата `0/1/2` стали `ExitCode`.
- Переменные переименованы: `valve` → `isValveOpen`, `moisture` → `moisturePercent`, `water` → `waterUsedLiters`,
  `operations` → `operationCount`, `code` → `actionCode`. Сравнение `valve == true` заменено на `isValveOpen`.

## Этап 3. Выделение чистых функций

Правила предметной области были размазаны по условиям внутри `main`. Теперь это отдельные функции
без ввода-вывода и без изменения внешнего состояния: результат зависит только от аргументов.

| Функция | Правило |
|---|---|
| `isValidMoisture(m)` | `0 ≤ m ≤ 100` |
| `canOpenValve(open, m)` | клапан закрыт и `m < 60` |
| `canWaterPulse(open, m)` | клапан закрыт и `m < 85` |
| `moistureAfterPulse(m)` | `min(m + 20, 100)` |
| `toAction(code)` | перевод числа в `Action` |

Все функции `constexpr`, поэтому граничные случаи (59/60, 84/85, ограничение до 100) проверяются
`static_assert` прямо при компиляции. Условия переписаны «положительно»: сначала успешная ветка, потом отказ.

## Этап 4. Устранение дублирования вывода

Что повторялось в legacy-коде:

- связка `operations++` + сообщение + `printStatus(...)` была скопирована в четырёх ветках;
- пара «приглашение → `cin >>` → `Input error`» была написана дважды.

Что стало:

- `promptInt(prompt, value)` печатает приглашение, читает число и сам сообщает об ошибке ввода;
- ветки `switch` только решают, что произошло, и задают `completedMessage` (успех) или `rejectedMessage` (отказ);
- счётчик операций и печать статуса после успеха выполняются в одном месте, сразу после `switch`.
  Отказ и неизвестный код по-прежнему не увеличивают счётчик.
